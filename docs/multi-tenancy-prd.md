# 多租户（组织采购模型）产品需求文档

> 文档状态：评审稿 v2
> 设计依据：`docs/multi-tenancy-design.md`
> 原型：`docs/multi-tenancy-prototype.svg`
> 适用范围：new-api 主仓库（Go 服务端、React 控制台、主数据库与日志数据库）
>
> **v2 相对 v1 的变更**：按 B2B 采购模型重写。删除 BYOK（组织自带渠道）与组织级定价覆盖；新增「组织采购订阅套餐」为核心功能；组织钱包与成员额度从 Phase 3 提升为 MVP；成员额度语义确定为共享池消费上限。

## 1. 背景

new-api 当前是「单租户、多用户」架构。用户、管理员、渠道、配置、账单和日志都处于同一个全局作用域；`group` 只承担定价、路由和限流职责，不是身份或数据隔离边界。

现有「一个用户 + 多个 API Key」的方式可以近似实现用量、模型、IP、渠道和限额隔离，但缺的不是配额能力，而是**采购主体与组织内治理**：没有可以统一采购、统一记账、再对内分配的聚合主体，客户成员也无法各自登录。

本次改动引入 `Organization + Membership` 模型，支撑如下商业模型：

**平台提供上游渠道、制定模型价格与订阅套餐 → 组织自助注册并在线购买套餐 → 额度进入组织钱包 → 组织管理员为成员设置消费上限 → 成员消费，由组织钱包统一结算。**

## 2. 产品目标

### 2.1 目标

1. 组织可以自助注册、在线购买平台定义的订阅套餐，额度进入组织钱包。
2. 组织管理员可以邀请成员、分配角色、管理组织内 API Key，并为成员设置周期性消费上限。
3. 组织管理员可以按组织聚合查看用量与账单，并下钻到成员、Key、模型和渠道。
4. 所有租户数据默认按组织隔离，平台管理员通过显式的跨组织入口管理全局资源。
5. API 请求无需新增数据库查询即可获得租户上下文，不降低 relay 热路径性能。
6. 存量用户与存量资源平滑迁移到个人组织，默认体验和现有计费结果保持不变。

### 2.2 非目标

- 不做 BYOK：上游渠道一律由平台提供，组织不接入自有渠道、不接触渠道密钥。
- 不做组织级定价覆盖：模型单价、group 倍率、套餐价格全平台统一，组织只能选套餐。
- 不把 `group` 直接改造成租户；`group` 继续承担「套餐 → 可用渠道与价格档」的职责。
- 不拆分全局用户与认证体系；密码、OAuth、Passkey、2FA 和 Session 继续属于用户。
- 不实现 database/schema per tenant；强物理隔离客户继续使用独立部署。
- 不把全部 `OptionMap` 租户化；SMTP、OAuth、支付密钥、模型定价保持平台全局。

## 3. 用户与使用场景

| 用户 | 核心诉求 |
|---|---|
| 平台超管 / 平台管理员 | 管理上游渠道池、模型定价、**订阅套餐定义**；必要时跨组织排障和审计 |
| 组织 Owner | 掌握组织全部权限，采购套餐、管理成员与资产，转让或停用组织 |
| 组织 Admin | 邀请成员、管理角色、API Key、成员消费上限，采购套餐，查看组织用量 |
| Billing | 查看组织账单与用量，采购套餐与充值，不接触成员和 Key 管理 |
| Member | 管理自己的 API Key，查看自己的用量和剩余可用额度 |
| 个人开发者 | 沿用现有体验：注册即进入个人组织，自己充值自己用 |

核心场景：

1. 个人开发者注册后自动进入个人组织，无需理解或配置「组织」。
2. 企业负责人自助注册团队组织，在控制台选购套餐并在线支付，额度进入组织钱包。
3. 负责人输入成员用户名发出站内邀请（绑定已有账号 ID），成员在通知中心接受或拒绝，接受后切换到该组织。
4. Admin 为成员设置周期性消费上限，成员自建 Key 并消费，由组织钱包统一结算。
5. Billing 查看组织预算、消耗趋势和订单，续订或升级套餐，但无法查看密钥或修改成员。
6. 套餐额度用尽后，按套餐的 `AllowWalletOverflow` 设置决定是否回落到组织钱包余额。

## 4. 核心产品模型

### 4.1 组织与成员

- `User`：全局身份，一个人只有一个登录身份。
- `Organization`：租户主体，分为 `personal` 和 `team`；承载钱包、订阅、成员与用量归属。
- `OrganizationMember`：用户与组织的成员关系，承载组织角色和成员消费上限。
- `OrganizationInvite`：按用户名绑定已有账号 ID 发出站内邀请；受邀账号在通知中心接受或拒绝，不使用邮件或邀请链接。
- 每位用户有且仅有一个个人组织；个人组织不可删除、不可转让。
- 一个用户可创建或加入多个团队组织。

### 4.2 商业模型与套餐

| 层级 | 由谁决定 | 内容 |
|---|---|---|
| 上游渠道池 | 平台 | 渠道、密钥、健康度、路由 |
| 模型单价与 group 倍率 | 平台 | 全平台统一 |
| 订阅套餐 | 平台 | 价格、周期、包含额度、对应档位（group）、成员数上限、额度耗尽是否回落钱包 |
| 采购决策 | 组织 | 选哪个套餐、何时续订、是否加购钱包余额 |
| 成员消费上限 | 组织 | 每个成员的周期性上限 |

- 套餐面向对象通过 `Audience` 区分（`personal` / `org` / `both`），个人套餐与组织套餐可以不同。
- 组织的有效档位由所购套餐决定；**成员不再各自持有档位**，全组织共享组织档位。
- 组织**不能**修改任何价格、倍率或套餐内容；想要更低单价只能升级套餐档位。

### 4.3 角色模型

平台角色与组织角色相互独立：

| 组织角色 | 成员 | API Key | 用量/账单 | 采购套餐 | 成员上限 | 所有权操作 |
|---|---|---|---|---|---|---|
| Owner | 管理 | 全组织 | 查看 | 可 | 管理 | 转让、停用 |
| Admin | 管理 | 全组织 | 查看 | 可 | 管理 | 不可转让 |
| Billing | 不可管理 | 不可管理 | 查看 | 可 | 查看 | 不可操作 |
| Member | 仅查看自己 | 仅自己创建的 | 仅查看自己 | 不可 | 查看自己的 | 不可操作 |

最终权限以后端能力矩阵为准，前端显隐不能替代后端授权。

### 4.4 组织上下文

- 控制台在顶栏提供组织切换器。
- 前端保存 `active_org_id`，所有组织级请求携带 `X-Org-Id`。
- 服务端每次校验用户是否为该组织的有效成员，不能仅信任 Session 或请求头。
- API relay 请求从 Token 缓存直接读取 `org_id`，不得为租户解析增加同步数据库查询。
- 当前组织被停用、成员被移除或权限变化时，后续请求立即失败并引导用户切换组织。

## 5. 功能需求

### 5.1 组织切换器与组织列表（MVP）

- 顶栏显示当前组织名称、类型和用户在该组织中的角色。
- 下拉列表区分个人组织和团队组织，支持搜索。
- 支持自助创建团队组织；名称必填，Slug 自动生成并可编辑，需全局唯一。
- 切换成功后刷新能力矩阵、导航、数据列表和统计卡片。
- 若当前组织不可用，自动回退到个人组织并提示原因。

验收标准：

- 用户只能看到自己加入的组织。
- 切换后所有组织级接口均使用新组织上下文，页面不残留上一个组织的数据。
- 直接伪造 `X-Org-Id` 访问非成员组织返回 403，且不泄露组织是否存在。

### 5.2 成员与邀请（MVP）

- Owner/Admin 可按邮箱邀请成员并选择 `admin`、`billing` 或 `member` 角色。
- 邀请支持待接受、已接受、已撤销、已过期状态；支持重发与撤销。
- 邀请链接过期后不可使用，接受前需登录或注册匹配的用户身份。
- Owner/Admin 可修改非 Owner 成员角色、停用或移除成员。
- 组织始终至少保留一位 Owner；Owner 不能直接移除自己。
- Owner 转让必须由目标成员确认，完成后原 Owner 降为 Admin。
- 套餐规定成员数上限时，超限邀请被拒绝并提示升级套餐。

验收标准：

- 同一用户在同一组织只有一条有效成员关系。
- 非 Owner 无法执行所有权操作；Admin 无法提升任何人为 Owner。
- 被移除成员的组织访问权限立即失效，其已创建 Key 的处置遵循组织资产规则，不随成员删除。

### 5.3 组织级 API Key（MVP）

- Key 创建时必须绑定当前组织和创建者。
- Admin/Owner 可查看和管理组织内全部 Key；Member 只能查看和管理自己创建的 Key。
- Key 列表展示名称、创建者、状态、模型限制、IP 限制、Key 级额度和最近使用时间。
- 明文 Key 仅在创建成功时展示一次，后续只显示掩码。
- 切换组织后，列表、创建和编辑操作只作用于当前组织。

验收标准：

- Token 缓存包含 `org_id`，relay 请求上下文无需额外查库。
- 任何读写操作都必须同时满足组织 Scope 和角色权限。
- 平台管理员跨组织查询使用独立入口，不允许以 `org_id=0` 绕过过滤。

### 5.4 组织用量与审计（MVP）

- Owner/Admin/Billing 可查看组织总用量、趋势、Top 模型、Top 成员和 Top Key。
- Member 只能查看自己的用量及自己创建 Key 的明细。
- 日志筛选支持时间、成员、Key、模型、渠道和请求状态。
- 管理写操作记录组织、操作者、动作、对象和结果。
- 平台管理员可通过显式入口跨组织检索；普通组织入口始终强制组织过滤。

验收标准：

- 主日志库、独立 `LOG_DB` 和 ClickHouse 路径均包含并可过滤 `org_id`。
- 成员用量聚合结果与组织钱包扣费总额在同一周期内可对账。
- 组织 A 的用户无法通过搜索、分页、导出或详情接口读取组织 B 的数据。

### 5.5 组织套餐采购与支付（MVP）

- 控制台展示平台定义的、`Audience` 匹配组织的套餐列表：价格、周期、包含额度、对应档位、成员数上限。
- Owner/Admin/Billing 可下单；下单生成归属组织的订单，同时记录操作人。
- 支持现有在线支付渠道（Stripe / Creem / Waffo / Waffo-Pancake / 易支付）。
- 支付成功后额度进入**组织**钱包或组织订阅额度；组织档位按套餐 `UpgradeGroup` 更新。
- 套餐到期按 `DowngradeGroup` 或购买前档位回退。
- 消费优先级：组织订阅额度优先，耗尽后按 `AllowWalletOverflow` 决定是否回落组织钱包。
- 订单历史对 Owner/Admin/Billing 可见，含订单号、套餐、金额、状态和时间。
- 组织不可修改套餐价格与内容；控制台明确提示价目表全平台统一。

验收标准：

- **支付回调只信任订单记录里持久化的 `org_id`**，不信任回调参数中的任何身份字段。
- 重复回调、乱序回调和回调重试保持幂等，不产生重复入账。
- 套餐额度、钱包余额和档位变更三者在一次成功支付后状态一致；任一步失败不留中间态。
- 个人组织沿用现有个人套餐路径，购买与到期行为与迁移前等价。

### 5.6 组织钱包与成员消费上限（MVP）

预算层级为：**组织订阅额度 / 组织钱包（唯一权威扣减点）→ 成员周期消费上限（前置检查）→ Key 硬限额（前置检查）**。

- 采用**共享池 + 上限**语义：成员上限不从组织池划走额度，组织池耗尽则所有成员停止。
- 权威扣减只发生一次，落在组织订阅额度或组织钱包。
- 成员上限和 Key 限额是预检查，不参与最终对账；触顶请求被拒绝且不触碰组织余额。
- 成员已用量按周期统计，数据来源为组织 + 成员维度的用量聚合，不作为账本。
- 组织钱包使用 `int64/bigint`；所有换算、取整、饱和和异常审计遵循现有计费安全不变量。
- 预扣、结算、退款和订阅额度必须以同一组织为主体。
- 个人组织迁移前后的余额、扣费与订阅行为保持等价。
- 支持预算告警：达到设定百分比时通知 Owner 与 Billing。

验收标准：

- 超额请求在预扣阶段失败，不产生负费用、不发生整数溢出。
- 成员触顶不影响同组织其他成员，也不消耗组织余额。
- 所有饱和事件进入请求关联日志和管理员可见审计信息。
- 余额缓存与数据库故障回退、并发扣减、退款和重试均保持幂等。

### 5.7 组织设置（Phase 3）

只允许覆盖**非定价**白名单字段：

| 允许 | 不允许 |
|---|---|
| 组织显示名、Logo | 模型单价、group 倍率、加价率 |
| 通知 Webhook / 告警邮箱 | 套餐价格与内容 |
| 成员默认消费上限 | 可用档位（由套餐决定） |
| 可用模型的**收窄**子集（只能在套餐授权范围内减，不能扩权） | SMTP、OAuth 应用、支付密钥 |

- 全局默认值与组织覆盖合并为 Effective Settings，缓存按 `org_id + version` 失效。
- 组织设置页不包含任何渠道或价格相关入口。

### 5.8 组织生命周期（Phase 3）

- 团队组织支持停用、恢复、所有权转让和删除申请。
- 删除采用软删除 + 后台异步清理，不能同步级联删除。
- 删除前展示受影响的成员、Key、日志、账单和订阅。
- 存在未到期订阅或未结清余额时，删除需二次确认并说明余额处置规则。
- 个人组织不可删除。

## 6. 控制台信息架构

顶栏新增组织切换器；侧边栏按当前组织能力展示：

- **概览**：组织用量、预算状态、成员与 Key 摘要。
- **API Key**：组织级 Key 列表和创建流程。
- **用量日志**：组织/个人视角按权限过滤。
- **成员**：成员列表、邀请和角色管理。
- **账单与预算**：钱包余额、当前套餐、成员消费上限、预算告警。
- **套餐与订单**：平台套餐选购、当前订阅状态、订单历史。
- **组织设置**：基本信息、通知、模型收窄与危险操作（Phase 3）。

平台管理导航（渠道、模型定价、套餐定义、系统设置）保持独立，只对平台角色展示。**组织侧导航不出现渠道入口。**

## 7. 关键交互流程

### 7.1 创建并切换组织

用户打开组织切换器 → 创建组织 → 填写名称/Slug → 创建成功 → 成为 Owner → 自动切换到新组织 → 展示空状态与「选购套餐 / 邀请成员」引导。

### 7.2 选购套餐

Owner/Admin/Billing 打开「套餐与订单」→ 对比套餐（价格、包含额度、档位、成员上限）→ 选择套餐 → 确认组织归属与金额 → 跳转在线支付 → 回调入账 → 钱包/订阅额度与组织档位更新 → 订单进入历史。

失败路径：支付超时或失败保留待支付订单，不改变余额与档位；重复回调不重复入账。

### 7.3 邀请成员

Admin 打开成员页 → 点击「邀请成员」→ 输入用户名并选择角色 → 发出站内邀请 → 被邀请人在通知中心接受或拒绝 → 成员列表实时更新。重复邀请、已是成员或超出套餐成员上限时提供明确、不可枚举其他组织信息的错误提示。

### 7.4 设置成员消费上限

Admin 打开账单与预算 → 成员预算表 → 为成员设置周期上限 → 保存后下一次请求生效 → 成员在自己的概览页看到剩余可用额度。

### 7.5 创建组织 Key

用户在当前组织打开 API Key → 创建 Key → 配置名称、模型、IP 和 Key 级限额 → 二次确认组织归属 → 创建成功 → 一次性复制 Secret。

### 7.6 跨组织切换

用户切换组织 → 清空组织级页面缓存和未提交表单 → 拉取新能力矩阵 → 跳转到新组织的同类页面；若无权限访问该页面，则回到组织概览。

## 8. 数据与权限要求

- 新增 `organizations`、`organization_members`、`organization_invites`。
- 以下租户数据增加 `org_id`：`tokens`、`logs`、`user_subscriptions`、`subscription_orders`、`topups`、`tasks`、`midjourneys`、`redemptions`、用量统计表、审计表。
- `channels` 与 `abilities` **不加 `org_id`**（BYOK 非目标），渠道路由与索引保持不变。
- `SubscriptionPlan` 扩展 `Audience` 与成员数上限字段。
- 所有租户列表和详情查询通过统一 `OrgScope`；跨租户查询使用语义明确的独立方法。
- Casbin 从 `sub, obj, act` 升级为 `sub, dom, obj, act`，`dom=org:<id>`；平台策略使用 `*`。
- 组织权限资源包含 `org.member.*`、`org.token.*`、`org.billing.*`、`org.subscription.purchase`、`org.settings.write`；**不包含** `org.channel.*`。
- 业务资源创建时必须明确赋值 `org_id`，不允许产生无主租户数据。
- 组织删除为软删除并由后台任务清理跨主库、日志库和策略表的数据。

## 9. 非功能要求

### 9.1 安全

- 组织隔离必须覆盖列表、详情、搜索、导出、批量操作、异步任务回查和审计。
- **支付回调归属**是本次新增的高危面：归属只来自订单记录，回调参数不参与身份判定。
- 邀请 Token 只保存哈希；Key Secret 只展示一次。
- 组织不存在与无权限访问使用一致的外部错误语义，避免枚举。
- 权限变更、成员移除和组织停用应在下一次请求生效。

### 9.2 性能

- Relay 热路径解析组织上下文不得增加数据库查询。
- 组织过滤索引以 `org_id` 为最左前缀。
- 组织能力矩阵与 Effective Settings 必须可缓存并可可靠失效。
- 限流按 `org:group` 维度，避免单个成员打满整个组织配额。

### 9.3 兼容性与迁移

- 支持 SQLite、MySQL ≥ 5.7.8、PostgreSQL ≥ 9.6。
- 新建库、最新发布版升级、连续两次迁移幂等、独立日志库和 ClickHouse 路径均需验证。
- Phase 0 为所有存量用户创建个人组织并回填资源，暂不读取新列；Phase 1 再升级授权语义。
- 每个阶段可独立上线和回滚。

### 9.4 可用性与国际化

- 新增文案全部通过 i18n，覆盖 en、zh、zh-TW、fr、ja、ru、vi。
- 组织切换、角色变化、邀请过期、预算触顶和权限不足均提供明确恢复路径。
- 表格、对话框、下拉菜单和表单满足键盘操作、焦点管理和读屏标签要求。

## 10. 分阶段交付

| 阶段 | 范围 | 用户感知 |
|---|---|---|
| Phase 0 | 建表、加列、个人组织创建与数据回填 | 无 |
| Phase 1 | Casbin Domain、存量策略迁移（`dom="*"`） | 无 |
| Phase 2a | 组织上下文、切换器、成员/邀请、组织角色、组织 Key、组织用量视图 | 有，不碰钱 |
| Phase 2b | 组织钱包、套餐采购与支付回调改造、成员消费上限、档位作用于组织 | 有，高风险 |
| Phase 3 | 组织生命周期、组织设置白名单、平台跨组织后台 | 有 |

MVP = Phase 0 + 1 + 2a + 2b。「组织统一采购」是商业模型地基，无法推迟到 MVP 之后。

MVP 成功标准：企业客户可以自助注册组织、在线购买套餐、邀请多名成员各自登录、由管理员设置成员消费上限，并看到被严格隔离的组织用量与账单。

## 11. 成功指标

- 租户越权安全测试通过率 100%，线上跨组织数据泄露事件为 0。
- 支付回调入账准确率 100%，无错账、重复入账或归属错误。
- Relay P95 延迟相对基线无可归因于租户解析的显著回退。
- 存量用户个人组织迁移成功率 100%，迁移后余额和历史用量对账一致。
- 组织自助完成「注册 → 购买套餐 → 邀请成员 → 创建 Key」全链路的转化率与平均耗时。
- 组织管理员自助完成成员、Key、预算和用量查询的比例，及相关人工支持工单下降幅度。

## 12. 风险与待定项

### 12.1 风险

1. **越权风险**：管理端入口多、查询面广，必须用 OrganizationScoped 元测试和接口级安全回归覆盖。
2. **支付回调归属风险**（新增）：五个回调入口都要改为向组织入账，任何从回调参数推断归属的写法都可能被用来把额度打进他人组织。
3. **计费风险**：组织钱包引入 `int64` 聚合主体，需完整验证预扣、结算、退款、订阅和饱和审计。所选「共享池 + 上限」语义未引入第二个权威扣减点，风险小于硬划拨方案。
4. **日志一致性**：日志可能位于独立数据库或 ClickHouse，迁移与查询必须同步。

### 12.2 待定项

| # | 问题 | 当前处理 |
|---|---|---|
| 1 | 套餐计价维度：纯额度包 / 额度包 + 席位上限 / 纯按席位计价 | 按**额度包**为主线，成员数上限作为可选字段；纯按席位计价需另议 |
| 2 | 成员消费上限的周期口径：自然月 / 与订阅周期对齐 / 自定义天数 | 暂按「与组织订阅周期对齐」，待确认 |
| 3 | 组织能否在套餐授权范围内再收窄可用模型 | 暂按「允许收窄、不允许扩权」写入 5.7 |
| 4 | 个人用户与组织客户的注册入口是否分流；个人能否升级/合并为组织 | 未设计，需产品定 |
| 5 | 签到奖励 / 邀请返利归个人还是组织钱包 | 未改动，建议保持个人语义以避免多组织争议 |
| 6 | 成员移除后其 Key 与历史用量归属 | 建议 Key 始终归组织，创建者只用于权限与审计 |
| 7 | 是否需要发票 / 合同 / 对公转账 | 未设计；当前定位为自助在线支付 |
| 8 | 组织是否需要自有 SSO/OIDC | 未设计；会触碰「认证栈不动」的前提 |
| 9 | 组织 Slug | 用于展示和未来 URL；隔离判定只使用不可变的数值 ID |

## 13. 原型评审范围

`docs/multi-tenancy-prototype.svg` 覆盖桌面端核心路径，共 6 屏：

1. 组织概览与顶栏组织切换器。
2. 组织切换器展开态与创建组织入口。
3. 成员管理页与邀请成员对话框。
4. 组织级 API Key 列表与创建 Key 对话框。

不在本轮原型范围内：组织设置页与危险操作区、移动端适配、平台管理员跨组织后台、支付网关内部结算页。
